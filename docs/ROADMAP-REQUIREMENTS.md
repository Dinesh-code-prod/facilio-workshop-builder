## Part B. Master product enhancement (the requirement, in the order to build it)

Goal: one connected lifecycle. Customer Discussion → Requirement → Analysis → KPI → Solution → BRD → Configuration → Organization Export → Deployment Handover. AI helps and people decide. Capture once, understand once, validate once, reuse everywhere.

### B0. Phase order (change it only after saying why)
1. Foundation: audit, data model, traceability, workshops and sources, KPI register, Q&A register.
2. Solution and configuration intelligence: solution design, automation register, configuration inventory, configuration questions, dependencies, org ZIP analysis.
3. BRD document experience: custom BRD, section choice, rich editor, tables and screenshots, DOCX and PDF export and import, version comparison.
4. Documentation export and Claude handoff: project documentation package, task-specific context, connector, Claude solution document import with approval.
5. Organization export: configuration-to-export mapping, package builder, dependency validation, versioning, validation report.
6. Admin and executive intelligence: dashboards, teams, KPIs, risk, scope deviation, AI reporting, report export, scheduled reports, admin Claude handoff.
7. Testing and tuning: end to end, permissions, data integrity, import and export, large documents, AI accuracy, ZIP validation, regression.

### E12. Tasks automated, tracked by Claude, chased by Otto in Teams (user, 4 Nov 2026)
**Requirement.** Every task section inside a Delivery Studio project (the Project Tasks register, task board, governance actions, UAT issues, workshop action items, plan activities) is automated and tracked by Claude, and Otto (the facilio.work Teams bot) sends people direct messages with their pending tasks and what changed. Reuse the existing task register; no second task store (D-E rule).
**What exists today (read in the code, 4 Nov 2026).** One task register (`kind task`, owner must be a project member, due, eta, status, blocker, source), `GET /api/my/work` (a person's open, overdue, blocked tasks across projects), connector tools `list_overdue`, `portfolio_status`, `project_changes`, an alert helper `teamsPing` and `ctx.teams.send` already used for tickets (gated by the plain secret `teams_notify = on`). The platform has **no scheduler**, so nothing can run by itself at a set time.
**Design (programmer view).**
1. **Triggers, because there is no scheduler:** (a) event: a DM to the new owner when a task is assigned or the owner changes (built in slice 1); (b) on demand: Otto answers "my tasks" and "what is overdue" from the connector tools, and "send the team their pending tasks" runs `send_task_digest` after a Confirm click (slice 1); (c) a scheduled Claude routine that calls `send_task_digest` each morning as a project manager (needs the connector signed in and a decision on how an unattended run handles the Confirm step; **not verified**, ask the user); (d) later: page-open nudges.
2. **Spam and safety rules:** one digest DM per person per day (stored key); DMs only to project members who are not customers; skip people who muted the app (Otto reports `muted`); nothing is sent unless `teams_notify` is on; the result reports exactly what Teams returned (delivered, muted, failed), never an assumed success; no task text from customers is sent as an instruction.
3. **Claude tracking (slice 2, not built):** a connector tool that returns open tasks together with the evidence Claude needs (changes since a date, transcripts, minutes, UAT results, sign-offs) so Claude proposes status changes, new tasks from transcripts and e-mail-free sources, blocked items and due-date risks as **unapproved suggestions** with their source; a person accepts each. A spoken statement never closes a task by itself.
4. **Slices.** 1 (done in this change, see the progress log): `my_tasks` and `send_task_digest` connector tools, assignment DM, pure logic `work/server/_taskwatch.mjs`, tests. 2: Claude tracking tool and suggestion inbox in the task register. 3: due-soon and blocked rules, per-person preferences (mute, quiet hours), digest content for customers' actions kept separate. 4: scheduled routine once the user decides (c). 5: Teams action buttons (mark done, snooze) through `{ title, fn, data }` actions.
5. **Claude integration rule (CLAUDE.md):** every slice also updates the tool list in `work/work.json`, `CONNECTOR_HELP`, `docs/reference/claude-connector.md`, the Team Guide and the hand-off prompts; a changed tool list needs the connector removed and re-added in Claude.
6. **Not verified:** a real Otto conversation, a real DM delivery, the Confirm step in Teams, and a scheduled Claude run against the live app.

### E13. Support tickets through Facilio Support Desk, and links that open inside Delivery Studio (user, 4 Nov 2026)
**Requirement.** Support tickets use the existing Support Desk site (https://support-desk.facilio.run/#/homepage, built by another Facilio team on the Facilio Run platform) instead of the Studio's own Tickets and Inbox. Every external link (Support Desk, Meteor, Comet, facilio.com and the facilio.run sites chosen for the "Useful tools" list in E11) opens **inside Delivery Studio, like a browser page**, not in a new tab. This replaces the E5 plan to just remove Tickets from the navigation; the old Tickets and Inbox data stays.
**Findings (4 Nov 2026).**
- Support Desk and Delivery Studio are both behind the Facilio Microsoft sign-in (a request without a session is redirected to Amazon Cognito and Microsoft Entra). Support Desk lives on `facilio.run`, Delivery Studio on `facilio.work`: **different sites**, so a page framed from the Studio is a third-party frame. Browsers commonly block third-party cookies in frames, and Microsoft's sign-in page refuses to be framed, so the framed site may show a blank page or loop at sign-in. **Not tested**: the browser pane lost its sign-in, so a real framed load was not tried.
- The Studio's own page policy (`src/template.html`) allows frames only from itself (`frame-src 'self' blob:`), so any external site needs an explicit, narrow `frame-src` entry for that host, and the target site must allow being framed (its `X-Frame-Options` or `frame-ancestors`). Neither was readable without a session.
- Meteor and Comet are on `facilio.work` (same site as the Studio), so they are the most likely to work in a frame; facilio.com and the facilio.run sites are not known.
**Design.** One in-app "web page" view (`src/webframe.js`) that shows an allow-listed address in a frame inside the Studio shell, with a title, Back to Studio, and an always-visible "Open in a new tab" fallback (a blocked frame cannot be detected reliably, so show the fallback after a few seconds). The allow-list lives in one place and also drives the narrow `frame-src` entries. No page data is sent to the framed site. Ticket creation from Studio tasks and Claude is a separate step: first find out whether Support Desk has an API or connector (it is a Facilio Run site owned by another team; ask its owner), otherwise Claude files tickets by the existing `create_ticket` route into the Studio and a person copies across.
**Ways it can work, best first.** (1) Test whether the frame works for each target after signing in the pane (a five-minute test). (2) If Support Desk will not frame, ask its owner to redeploy it as an approved facilio.work app (same site as the Studio, cookies work) or to allow the Studio as a frame parent. (3) Fallback: open in a new tab with a clear "Support Desk" entry in the menu. **Built 4 Nov 2026 on a branch (not deployed): `src/webframe.js`, allow-list and `frame-src` hosts, menu entries; whether a real site renders in the frame is not checked.** See docs/reference/CONNECTORS-2026-11-04.md section 14.
