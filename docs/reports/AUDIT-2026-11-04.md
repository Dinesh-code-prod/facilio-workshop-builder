# Audit, 4 Nov 2026 (Part E step 0, and the "audit first" of Part D)

One audit for both: Part D0 ("audit first") and Part E step 0 ("audit plus connector discovery") are treated as the same piece of work, as E9 recommended. Connector findings are in [CONNECTORS-2026-11-04.md](../integrations/CONNECTORS-2026-11-04.md). Nothing was built, deployed or changed in the app for this audit.

**How it was done.** Read `HANDOFF.md`, `CLAUDE.md` and roadmap Parts D and E in full. Counted routes, menu entries and files in the code (`work/server/api.mjs`, `src/shell.js`, `src/workshubs.js`, `work/work.json`, `package.json`). Opened Meteor, Comet, Clari and facilio.run in the browser pane without signing in. Called read-only actions on the connectors.

**What this audit did NOT do.** It did not run `npm test`, the build, or any UI check today, so every "done" below rests on `HANDOFF.md`, the docs under `docs/reports/` and the test files that exist, not on a fresh run. It did not click through the live app. It did not read every one of the 128 source files; it read the structure and the files named in `HANDOFF.md`. The statuses are therefore "as recorded", marked **(recorded)**, unless a line says "seen today".

## 1. Architecture (seen in the code today)

| Layer | What it is | Size |
|---|---|---|
| Page | Plain-JavaScript single-page app. `src/*.js` bundled by `build.mjs` (esbuild) into `dist/`. Views register on `FWBViews`, actions on `ACT.<name>` (wired with `data-act` and `data-change`). No framework. | 128 JS files, about 3.26 MB; about 1,190 `ACT.` handlers |
| Server | One platform function `work/server/api.mjs` (2,069 lines, 349 KB) serving every `/api/*` route; `_ai.mjs` (AI), `_portfolio.mjs` (admin health), `_skills.mjs` (Facilio skills catalogue for Claude). Identity comes from the facilio.work platform (`ctx.viewer`), data in `ctx.db`, files in `ctx.files`. | 130 route definitions |
| Hosting | facilio.work (internal Facilio platform, same family as facilio.run). Review status is "pending", so only the owner and collaborators can open it. Deploys go only through the Facilio Work Apps connector. | site under 50 MB |
| AI | `_ai.mjs`: DeepSeek is the default; Claude only as an opt-in fallback with an organisation key (none configured on 3 Nov). | per-person rate limits, daily ceiling |
| Claude | A connector at `https://mcp.facilio.work/facilio-delivery-studio` with 31 tools (`work/work.json`), plus an "Open in Claude" hand-off engine (`claudelogic.js`, `claudehand.js`, `/handoff` routes). Replaced the Claude Desktop extension on 2 Nov. | 31 tools |
| Data | Platform key-value store. Records are generic items (`/items/:kind/:item`, about 40 kinds) and per-section documents (`/docs/:section`); big values are gzipped and split (limit about 100 KB per record). Files are chunked (16 MB parts) with per-category rules. | |
| Tests | `npm test` chains 19 Node test files (adapter, AI layer, portfolio, guide intelligence, org package, UAT, MSA, lifecycle, Claude launch, mail parse, customer mail, connector skills, org transition, demo project, timeline dependencies, onboarding rules, kick-off deck). About 75 files in `tests/ui` (Playwright; several known stale or failing, see `HANDOFF.md`). | |

**Server routes by area (130).** `projects/:id/*` 66 (ai 13, mail 9, files 9, tasks 4, tickets 3, items 3, handoff 3, feedback 3, docs 3, members 2, guide-responses 2, plus audit, search, open, discover, customer-access, ugd); `admin/*` 34; `mail/*` 7; `templates` 6; `me/*` 6; `auth` 3; `demo-project` 2; the rest single routes (health, knowledge, tickets, my/work, ai/status). The connector entry is `POST /api/` (the MCP tools).

**Important finding for the revamp.** There is **no generic push or pull layer**. What exists is a per-feature mix: the hand-off store (`/handoff`, one package, one answer, shown as a preview), `save_draft`, the item store, and a project audit log (`au.<project>` records written by `audit()` on create, update and a few other actions). There is no record of source, destination, version, status or validation per transfer, no duplicate guard across sources, and no status model like Not Retrieved / Retrieved / Approved / Pushed. That is the base E4 asks for and it has to be built first.

**Second important finding.** The Studio's **server has no Microsoft 365 file access**. Its only Microsoft Graph use is the mailbox sync (credential `graph_mail`, Mail.Read), which has not worked since the Microsoft 403 and is postponed. The Microsoft 365 reach that *does* exist is in the **user's own Claude session** (the M365 connector, see CONNECTORS). So "pull the MSA from Microsoft 365" is naturally a Claude-driven flow: Claude reads the file through the M365 connector and hands the extracted result to Delivery Studio through its connector. Making the Studio server read OneDrive itself would need a new Graph credential with file scopes granted by Microsoft admins; that is a decision for the review, not something to assume.

## 6. Risks seen

1. The connector set is a **Claude-session** capability, not a server capability. If a person has not added the M365 connector in their Claude, no MSA pull is possible for them. Each person's own access limits what Claude sees.
2. Meteor and Comet were assumed to be catalogue and UAT tools; they are not (CONNECTORS). Two Part E workspaces change shape.
3. `api.mjs` is one 349 KB file; adding push and pull to it increases risk. A separate server module is advisable.
4. Many UI checks are stale; the regression bar (E8 test 12) needs a trusted baseline first.
5. Large item records near the 100 KB value limit (gzipped and split); MSA text and transcripts are large.
6. The platform has no scheduler, so no timed sync; every pull is user-triggered.
7. Customer data handling: SharePoint search through the M365 connector reaches files across the Facilio tenant that the signed-in person can open (the test search returned 711 matches for "Master Services Agreement" including other people's drives). The pick-list must show only what the user chooses, and the stored copy needs the project's access rules.

## 7. Proposals for the review (not decided)

- **Data onboarding return:** self-contained HTML that produces a downloadable JSON package, returned by e-mail or by a project-specific upload link into the existing file store, then validated by the same rules as `onboarding_rules.mjs` before it touches records. Simplest, no customer account, reuses what exists. Alternatives are listed in E2.2.
- **MSA pull:** Claude-driven through the M365 connector plus new Delivery Studio connector tools (create project from extraction, attach source reference), with the extraction shown as a draft for the project manager to approve.
- **Module source:** org connection (`list-modules` and field actions) and saved org configuration (Kenny `org_config`), with a hand-entry fallback; Meteor only for the visual mockup/prototype reference.
- **Transcripts:** Teams meeting transcripts through the M365 connector if the meetings run in Teams; Clari if its connector is enabled and returns transcripts.
- **Navigation target (for the UI stage):** the six workspaces plus BRD, with Project (home, tasks, governance), Share with customer, Help, Settings. Tickets, Mail and marketing out.
