# Review of the 4 Nov 2026 build wave (found on 5 Nov 2026, NOT yet fixed)

Three independent read-only reviews of everything built since commit e470b94 (head then 7943193): `ecc:security-reviewer` (server), `ecc:code-reviewer` (browser), `ecc:silent-failure-hunter` (both). None found a critical issue. Nothing here was run in a browser or against the live platform. Each item should get a failing test first, then the fix (`ecc:tdd-workflow`), then `ecc:code-review` on the diff.

## Browser side
1. **HIGH** `src/msaflow.js` (~300, 322, 336): `draftWs` is a module-level cache not keyed by project. Project A's workshop-prep draft shows in project B, downloads under B's name and is saved into B on edit. Fix: cache by project id and rebuild when `S.project.id` changes.
2. **HIGH** `src/onbhtml.js` (~57, 102, 114): two elements with `id="files"` (section and file input). `$('#files')` returns the section, so chosen files never reach the package and the label points at the wrong element. Fix: rename the input, add a test that every generated id is unique and run the page script against a fake document.
3. `src/planfrommsa.js` (~76): a commitment matches the first regex hit, so "Go-live by 30 June 2027 subject to UAT sign-off" pins UAT. `readiness` and `train` (inside "constraint") match wrongly. "Today" uses UTC (wrong in IST 00:00 to 05:30). A date found in free text by `V.parseAnyDate` is labelled `contract`.
4. `src/msaflow.js` `planInput()`: ignores the timeline's working week (`td.cal.weekend`: sat, fri, sun, fri1), so Gulf projects get a Saturday-Sunday weekend.
5. "Use this plan" (`msaflow.js` ~311, `timeline.js` 55-56): snapshots only id, title, start, end (and only when no versions exist), then resets status and percent; the dialog says old rows stay. Dates from today or +90 days are saved as real dates; the "saved" toast shows before the server confirms.
6. `src/webframe.js` (~29): Reload does nothing on hash-routed sites (Support Desk `/#/homepage`, Meteor `/#/library`). A sign-in redirect to another host may be blocked by the page policy (only a signed-in browser run settles it).
7. `src/cfggap.js`: colliding row ids are dropped silently (readiness can read true with a missing row); `setInput` never clears `validated` and `deploymentReady`; module-keyed plain objects break on `constructor` or `__proto__`. `src/pkgvalidate.js:36` uses `in` for attribute repeats.
8. Validators: `src/onbreturn.js` rejects the whole package for an unknown checklist id (should warn and drop), accepts a file with no size or a bad extension; `src/ftrresult.js` skips the project check when the file has no project id; an onboarding package submission reads as "Data workbook updated" (`onboarding.js` `onbPkgSave`).
9. Accessibility and async: Transfers filter selects lose focus on every change; repeated Accept, Dismiss and Show buttons and an empty `<th>` have no distinguishing names; `xfOpen` can show a late response for a different transfer; `xfClaude`, `tkTrack`, `sqClaude` have no try/catch or busy guard; `sgLoad` failure shows an empty list for 30 s.
10. `src/kickoffhtml.js` `shell` lacks `base-uri 'none'; form-action 'none'`; `mfWsPreview` opens a blob without `noopener`; ZIP validation (`orgpkgview.js` ~165) has no running size cap and uses a private JSZip field; the UAT guide shows internal gaps to the customer; small: mis-indented `const api`.

## Server side
A. **create_project_from_msa** (`_msaapi.mjs`): project created, then the link or the fill can fail; a retry then says "already created" with a half-empty project, or creates a second project; `existing()` does not check the project still exists and shows its id to non-members; the lock is per process.
B. **Tasks** (`_tasksapi.mjs`): accepting a `create` suggestion twice makes two tasks (random id); a stale suggestion overwrites newer edits (no task version or previous values stored); `.catch(() => [])` in `tasksById`, `task_evidence`, `taskRowsOf` makes read errors look like "no tasks" or "nothing pending"; a dismissed suggestion blocks an honest one with the same fields.
C. **Prepared questions** (`_questionsapi.mjs`): a docRead failure looks like "no questions"; a module named `__proto__` or `constructor` crashes; one RegExp per module pair is unbounded.
D. **Transfer rules** (`_transfer.mjs`, `_transferapi.mjs`): `pushGuard` never compares `destRef` with the intent's destination; `destEtag` optional; `transfer_report` failed needs no nonce; the app route `/transition` can set Pushed or Synchronized by an editor with a visible sha; approval does not require `ver`; `validation.ok` from Claude is not marked self-reported; `transfer_store` retry on a duplicate sha never advances a stuck status; `msa_extraction_save` note is wrong in non-submitted and duplicate cases; transfer outputs lack the `untrusted` marker.
E. **Storage and abuse**: dropped versions' payloads (`xfd.`, `xfdp.`) are never deleted; no cap on transfers or bytes per space; no per-person limit on `store` (about 1.2 GB per 10 minutes possible); holding data is never deleted with a person's data.
F. **Teams**: the self digest scope is free text (any substring gives a new key, so the once-a-day guard is bypassable); `again` unlimited; no `limit('digest')` bucket; the assignment DM carries task-title text with links and does not say who assigned it; the counter is taken before the send; the digest returns raw Teams replies and `e.message`; 30 sequential sends without a time budget.
G. **Authorisation**: the handler runs any key of CONNECTOR from the `x-work-mcp-tool` header, including the old implementation names (`transfer_push_begin`, `transfer_report`, ...), so `confirm: true` on `transfer_push` can be bypassed if the gateway or a browser forwards such a name (not verified); the holding space grants write to sub admins and customer-role members; `POST /api/projects` has no sub-admin check.
H. **`_msaextract.mjs`**: project `type:'cmms'` hard-coded; the contract term takes the first number only ("2 years 6 months" gives 24); dates with an `interpreted` or `assumed` origin are applied as contract facts.

Pre-existing, also noted: any project member (including customers when access is on) can read any doc section through `GET /api/projects/:id/docs/:section`, so MSA data written into `planner` is visible to them.
